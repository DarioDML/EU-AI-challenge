# Policy tool: if the 2021 flood returned tomorrow

Interactive assessment for Anna, cross-border crisis coordinator for the Belgian provinces of Liège and Limburg, Dutch Limburg and Region Aachen. It answers her question — *would we be better prepared if the 2021 flood returned tomorrow?* — for the six areas Copernicus EMS mapped in her region, and proposes one action: a cross-border shelter register, so that every flood alert names a shelter.

| View | Answers |
|---|---|
| 1 · Region | Q1 homes and residents in the mapped flood, Q2 status of measures since 2021, Q3 shelter coverage, Q4 ranking of the most exposed areas |
| 2 · Zoom in | One area along the warning chain Detect → Interpret → Decide → Alert → Johan, with live shelter matching and the alert on a phone, including the walking route from the home to its shelter |
| 3 · Anna's action | The recommendation, the ranking and the full Q2 evidence grid |

## Open it

```powershell
python -m http.server 8765 --directory policy-tool
```

Then open <http://localhost:8765>. In view 2, use ← / → for the steps and click any home to see its alert. The plan sliders re-run the matching for all areas. For submission, build one self-contained page (data inlined; Leaflet, map tiles and walking routes still need internet):

```powershell
python scripts/bundle_policy_tool.py
```

## Deploy (Vercel)

Static site, no build step: Root Directory `policy-tool`, Framework Preset "Other", build command empty. Every merge to `main` redeploys. A missing `data/<area>.js` only drops that area from the page.

## Q2 evidence (Researchers)

Edit `q2_evidence.csv` (Excel works; keep UTF-8). One row per area and theme; `area_id` is `region`, `be_01`, `nl_01`, `de_08`, `de_09`, `de_10` or `de_18`; `status` is `verified` (finding + source), `claimed` (announced, not confirmed) or `unknown`. The `lead` column says what to look for. Then run:

```powershell
python scripts/build_q2_evidence.py
```

It refuses rows without a source for `verified`/`claimed` and links that are not http(s).

## Data and method

`data/<area>.js` is generated by `python scripts/build_shelter_alert_data.py` (all six areas; `--aoi be_01` for one), which also writes `data-analysis/shelter_alert_<area>_summary.json` and `..._shelters.csv`.

| Input | Use |
|---|---|
| `data/reference/aoi_event_unions.parquet` (EMS EMSR517/518/520) | Mapped 2021 flood (water + flood traces) |
| GHS-OBAT R2024A BEL, NLD, DEU | Residential points inside the flood; footprint and height of shelter buildings, across borders |
| GHS-POP R2023A E2020 30″ | Residents per cell, shared among residential buildings by floor area |
| EFAS RP100 / RP500 depth | Coverage check of homes; shelters with RP500 depth can be excluded |
| OpenStreetMap via Overpass (cached in `data/raw/osm/`) | Schools, sports halls, community buildings, care sites, village names |
| FOSSGIS OSRM foot router (`routing.openstreetmap.de`), fetched live per selected home | Walking route and turn-by-turn steps in the alert, and how many metres of it lie in the 2021 flood |

Checks run by the build script: homes in the flood and homes with RP500 and RP100 depth must equal `data/reference/aoi_metrics.csv`; the build stops otherwise. The page recomputes the matching in the browser and reproduces each summary JSON at the default plan.

Default plan: 3.5 m² per person, 50 % of floor area usable, storeys = height ÷ 3 m, shelters more than 50 m from the 2021 flood and without RP500 depth, nearest-shelter-with-room-first matching on straight-line distance up to 5 km, across national borders. Limits are listed at the bottom of the page.
